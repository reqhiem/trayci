# Compatibility matrix

| Distribution    | Desktop            | Tray/window startup | Popover |  Autostart |  Claude |   Codex | Antigravity |
| --------------- | ------------------ | ------------------: | ------: | ---------: | ------: | ------: | ----------: |
| Linux Mint 21.3 | Cinnamon / X11     |                Pass |    Pass | Pass (E2E) |    Pass |    Pass |  Pass (CLI) |
| Ubuntu 25       | GNOME              |                Pass |    Pass |       Pass |    Pass |    Pass |     Not run |
| Ubuntu 25.10    | GNOME 49 / Wayland |                Pass | Partial |    Not run | Not run | Not run |     Not run |

The Mint and Ubuntu 25 (GNOME) rows were checked with the packaged Electron runtime, real local provider sessions, the renderer E2E, and XDG autostart writing in an isolated configuration directory. Antigravity's four quota windows were validated on Mint against a signed-in `agy` 1.1.11 session; packaged popover validation remains pending.

The Ubuntu 25.10 row was checked against the Tauri build (v0.4.2 plus the drag fix below) with a debug binary, opening the popover from the tray menu. Usage from the local provider sessions rendered, but was not checked against the CLIs. The popover is Partial because it cannot be placed on Wayland; see below.

**Note:** as of v0.3.0 Trayci runs on Tauri 2. The matrix above reflects the retired Electron build and is pending re-validation against the Tauri build (see tech spec §19 for the known Tauri/Linux watch-items).

**Dragging, on every platform:** until the drag fix, the title bar could not move the popover anywhere, and not for the reason first recorded in issue #37. Tauri's drag script answers a press on `data-tauri-drag-region` by invoking `start_dragging`, which needs `core:window:allow-start-dragging`. `capabilities/default.json` granted only `core:default`, which does not include it, so the command was refused before it reached `tao`. With the permission granted the window manager moves the window, and the app only records that a drag began and where the popover came to rest. The manager keeps the pointer for the whole move, so the release never reaches the webview: the drag ends at the first pointer event that arrives with the button up.

**X11:** measured on Linux Mint / Cinnamon (muffin) against v0.4.0: dragging the title bar did nothing, and the popover mapped unfocused with `_NET_WM_STATE_DEMANDS_ATTENTION`. Both were put down to the zero timestamp `tao` sends — `begin_move_drag(.., 0)` and `present_with_time(GDK_CURRENT_TIME)`. For focus that held: as of v0.4.1 the app asks for focus with a timestamp read from the X server, and click-outside was confirmed on that session. For dragging it did not, since the request never left the webview (above). v0.4.1 worked around it by following the cursor with `set_position` while the header was held; that path is gone.

The native move was measured on muffin 6.4.1 — Ubuntu's `muffin` package running as the window manager of an Xvfb display, not on Mint itself. `begin_move_drag(1, x, y, 0)` issued from an idle callback, as `tao` does, moves the window exactly like a request carrying the event time. In the app, a header drag moves the popover, stores `windowPosition` where it came to rest, a press that moves nothing stores nothing, clicking outside afterwards closes it, and it reopens at the stored position. **Still to confirm on Mint 21.3's own muffin before release.**

As of v0.4.2 a saved position is clamped to the work area of the monitor it was saved on rather than the one under the pointer, so opening from the tray menu no longer pulls the popover onto the panel's screen.

One thing is still open on X11: the first key after the popover is shown is dropped roughly every other open, so Escape sometimes needs a second press. Any other keypress flushes it. It correlates with the popover being hidden while it still holds focus, and is not the input method — reproduced identically with `GTK_IM_MODULE=gtk-im-context-simple`. Tracked in issue #38; click-outside is unaffected.

**Wayland:** measured on Ubuntu 25.10, GNOME Shell 49. The popover drags: the compositor moves it, and clicking outside closes it afterwards. It cannot be placed by the app — `gtk_window_move` is a no-op for a Wayland toplevel — so it neither anchors to the tray icon nor reopens where it was left. After a drag, `set_position(300, 300)` returns `Ok` and the popover stays where it was dropped, and `outer_position` reads `(0, 0)` wherever the window is, so there is no position to store either; `windowPosition` stays `null`. mutter does not advertise `xdg_session_management_v1`, the protocol that would let a client restore where its window was. It does advertise `xdg_activation_v1`, which has not been tried for focus yet (issue #38). `always_on_top` is not honoured either (tauri#14913), so the popover can open behind other windows.

XWayland is not a way out, and the app must not force it. Measured on Ubuntu GNOME with `GDK_BACKEND=x11`: the popover maps but never takes X input focus (`xdotool getwindowfocus` keeps naming another window), and the first click unmaps it instead of reaching the webview — the settings button, the refresh button and the provider rows all appear dead. Pointer motion still arrives, so hover keeps working, which is what makes the failure look like "only the header broke".

**Windows:** not measured, so there is no row. The capability file is the same on every platform, so before the drag fix the title bar could not have moved the popover there either. With the permission, `start_dragging` reaches `tao`, which releases mouse capture and posts `WM_NCLBUTTONDOWN` with `HTCAPTION`: the system's own move loop, with no window manager or timestamp involved. To verify on a Windows machine with `pnpm dist:win`: the header drags; `windowPosition` is stored when it is released, which relies on `WindowEvent::Moved` arriving during the move loop and on a pointer event reaching the webview after it; click-outside closes the popover afterwards; and it reopens at the stored position.
